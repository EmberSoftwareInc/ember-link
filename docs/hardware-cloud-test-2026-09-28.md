# Local backend and physical cloud delivery — 2026-09-28

## Scope

One ESP32-S3 Ember Link dongle, approximately 126 MB FAT16 microSD, connected
to a Mac over USB and to Wi-Fi. The `ember-app` disk-backed cloud service ran
on the Mac. With explicit user approval, a temporary Cloudflare HTTPS tunnel
forwarded only device polling and signed download routes. Account routes were
blocked at the tunnel proxy. Test credentials were disposable; payloads sent
through the tunnel were generated bytes, not existing user designs.

This verifies transport and storage, not embroidery-file validity or operation
on an embroidery machine. No AWS resources or production accounts were used.
The setup proof was sent with a Python USB client, not a browser UI.

## Firmware and TLS finding

- Updated the device from signed `0.1.0-dev` to signed `0.3.0-dev` over USB.
  Wi-Fi settings and the existing SD file were preserved; boot confirmation passed.
- The initial physical poll failed during the TLS handshake, before reaching the
  backend. Numeric USB diagnostics reported HTTP status 0, HTTP error 28674,
  transport error 32794, TLS error 12288, and verification flags 0.
- The tunnel presented a Google Trust Services chain containing a cross-signed
  GTS Root R4 certificate. Enabling
  `CONFIG_MBEDTLS_CERTIFICATE_BUNDLE_CROSS_SIGNED_VERIFY=y` fixed the connection.
  Subsequent polls returned HTTP 200 with no transport/TLS errors. The trusted
  root bundle and hostname verification remain enabled; no private CA or
  certificate bypass was added.
- Added credential-free `cloud_status.network` diagnostics for the last API
  attempt: stage, HTTP status, connection error, socket errno, transport error,
  TLS error and verification flags. Successful attempts clear stale errors.
- Final flashed image SHA-256:
  `15993f56bfa2194754f088658352334c0557e41351c04963b61656b8d80b6bd4`.
  It reports `0.3.0-dev` and includes the testing branch's TLS/diagnostic changes.

Fresh builds inherit the cross-signed setting from `sdkconfig.defaults`.
Existing build directories must also enable that option in their generated
`sdkconfig` (for example through `idf.py menuconfig`) and rebuild; defaults do
not override a previously saved disabled setting.

## Physical results

- A fresh setup session was claimed using a short-lived USB proof echoed by the
  real dongle over authenticated HTTPS. The backend confirmed ownership and
  online state.
- Delivered these generated payloads sequentially to the same temporary root
  filename, verifying both larger and smaller replacements:

| Bytes | Time to receipt and USB readback | Result |
| ---: | ---: | --- |
| 131,072 | 18.77 s | done; SHA-256 matches |
| 1,048,576 | 29.01 s | done; SHA-256 matches |
| 65,536 | 20.62 s | done; SHA-256 matches |

Times include polling, HTTPS download, SD write, receipt acknowledgement, and
USB remount/readback; these are smoke-test observations, not throughput targets.
The Mac volume was unmounted before each device-side write. Each write forced
USB refresh and remount. The pre-existing file's SHA-256 remained unchanged.
Final diagnostics reported 166,472 bytes free heap, a 110,728-byte minimum,
and a confirmed boot. Largest free block, stack headroom, and long-term heap
stability were not measured.

## Local automated and separate-process checks

- 40 backend tests passed, including authorization boundaries, claim proofs,
  concurrency, immutable downloads, receipts, failure handling, firmware-update
  state transitions, and HTTP delivery.
- 7 browser setup unit tests passed with simulated serial I/O.
- All four native firmware suites passed with ASan/UBSan, including new coverage
  for connection diagnostics, credential omission, and clearing stale errors.
- An independent Node device-simulator process received 1 KiB, 1 MiB, and 8 MiB
  payloads with exact byte verification, plus same-name replacements.
- Corrupt uploads were rejected; cancellation prevented delivery. Restarting
  the backend process preserved queued/completed jobs, and restarting the
  simulator delivered the pending job without delivering cancelled/corrupt files.

## Cleanup and remaining work

Removed the generated file through the authenticated local API and revoked its
temporary local pairing. The original SD root files match the pre-test hashes.
Cloud is disabled; the dongle retains a disposable test enrollment in NVS and
must be provisioned for the intended service before enabling cloud again.
The temporary backend, proxy and HTTPS tunnel were stopped. Wi-Fi settings and
the signed firmware update remain installed. Nothing was deployed or published.

Still required: actual embroidery-machine reads of valid designs, production
AWS/Cognito/S3/IAM integration, physical cloud OTA/rollback, interrupted power,
missing/full cards, physical lost-ack/retry and revocation cases, browser UI
setup, and sustained transfer/idle tests. Simulator tests do not substitute for
these hardware and deployment checks.
